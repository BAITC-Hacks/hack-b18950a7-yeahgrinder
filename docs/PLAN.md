# План: 5 часов, 3 человека

**Цель к финалу:** менеджер выбирает категорию → жмёт «Рассчитать» → видит заказы ИЭК
со срочностью и обоснованием → открывает товар и видит на графике, что убрано и что
добавлено → правит количество → утверждает → скачивает XLSX. Плюс экран «Проверки»,
где все 5 must-have прогоняются вживую.

**Стек:** Python + pandas (расчёт) + Streamlit (интерфейс). Одна кодовая база, запуск
одной командой. Данные — реальные из IEK.zip (`docs/DATA.md`).

## Алгоритм (коротко)

Для каждого товара, по месяцам:

1. **Чистка разовых заказов.** Строка накладной — разовая, если она сильно больше
   обычной строки этого товара (медиана + 6·MAD и минимум 5× медианы) и в одиночку
   даёт большую часть продаж месяца. Такие строки не считаем регулярным спросом.
2. **Упущенный спрос.** Месяц без остатка на начало — спрос в нём занижен. Заменяем на
   ожидаемый (по соседним месяцам с учётом сезонности), если он больше факта.
3. **Прогноз.** Уровень спроса без сезонности × сезонный коэффициент месяца (свой у
   товара, если истории хватает, иначе группы, иначе компании) × тренд × прирост из
   настроек.
4. **Заказ.** Спрос на (срок поставки + период до следующего заказа) + страховой запас
   − остаток − в пути → округляем вверх до кратности MOQ.
5. **Срочность.** На сколько дней хватит запаса vs срок поставки.
6. **Обоснование** — шаблонный текст из всех чисел выше.

## Кто что делает

Три агента работают параллельно. Правило одно: **каждый трогает только свои файлы**,
иначе конфликты в git съедят больше времени, чем сэкономят агенты.

| Поток | Агент | Свои файлы | Задачи |
|---|---|---|---|
| **A. Расчёт** | Claude (этот) | `engine/` | Загрузка, чистка выбросов, упущенный спрос, прогноз, заказ, обоснование; тюнинг на реальных данных |
| **B. Интерфейс** | Codex | `app.py`, `ui/` | Streamlit: таблица по поставщикам, карточка товара с графиком, правка и утверждение, экспорт XLSX |
| **C. Проверки и защита** | Claude №2 | `checks/`, `README.md`, `docs/pitch*` | Скрипты 5 проверок must-have; README (методология, выбросы, запуск); презентация и сценарий демо |

Человек за каждым агентом смотрит на результат глазами и сверяет цифры с Excel по 5–10
товарам — агенты этого сами не сделают.

**Git:** каждый поток — своя ветка (`engine`, `ui`, `checks`), в `main` мержим часто,
минимум раз в час. Коммиты от своих аккаунтов, без подписей AI.

## Контракт между расчётом и интерфейсом

B и C могут начинать сразу, не дожидаясь готового расчёта: пока его нет, достаточно
заглушки с такими же колонками.

```python
from engine.compat import load
from engine.compat import Params, compute

ds = load()                      # читает data/raw/IEK/ (распаковать IEK.zip туда)
res = compute(ds, Params())      # ~секунды на все товары
```

`Params`: `review_days=30` (период до след. заказа), `lead_days=30` (срок поставки по
умолчанию), `service_level=0.95`, `growth_pct=0.0` (прогноз прироста, %),
`oneoff_k=6.0` (строгость отсечения выбросов), `groups=None` (фильтр категорий).

`res.orders` — одна строка на товар:

| колонка | смысл |
|---|---|
| `code`, `article`, `name`, `unit` | код 1С, артикул ИЭК, название, ед. |
| `group`, `group_name`, `supplier` | категория (префикс кода), её название, поставщик |
| `base_month` | регулярный спрос в месяц (без выбросов, с упущенным) |
| `forecast_need` | прогноз спроса на срок поставки + период |
| `safety_stock` | страховой запас |
| `stock_now`, `in_transit` | остаток сейчас (оценка), в пути к сроку |
| `moq` | кратность |
| `order_qty` | **рекомендуемый заказ** (0 — не заказывать) |
| `days_cover`, `lead_days` | на сколько дней хватит запаса; срок поставки |
| `urgency` | `критично` / `высокая` / `плановая` / `не нужно` |
| `reason` | текст обоснования |
| `n_oneoff`, `lost_qty` | сколько разовых строк исключено; сколько спроса досчитано за stockout |

`res.history` — для графика: `code, month, raw_qty, oneoff_qty, lost_qty, clean_qty, forecast`.
`res.oneoffs` — исключённые строки: `date, doc, code, qty, threshold`.

  РФ ≈ 35–40 дней, остальное 12–24).
