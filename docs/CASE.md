# Кейс: ТОО «Электрокомплект» (ekt.kz) — HACKALEM AI

Автоматический расчёт заказов поставщикам для пополнения склада.

## Проблема и ценность
Менеджер отдела закупа рассчитывает потребность в пополнении склада вручную, консолидируя данные в Excel. Из-за трудоёмкости расчёт проводится нечасто и не в реальном времени → избыточные запасы по одним позициям и дефицит по другим. Разовые крупные заказы (в т.ч. крупные продажи одному клиенту) искажают расчёт регулярной потребности → лишние издержки на хранение и упущенные продажи.

Ценность: снижение издержек на избыточное хранение, сокращение дефицита и упущенных продаж, повышение точности регулярных закупочных решений.

## Пользователь
Менеджер отдела закупа. Сценарий: запускает расчёт по складу или категории → получает список рекомендованных заказов поставщикам с обоснованием по каждой позиции → проверяет, корректирует → утверждает заказ.

## Задача
Сервис, который на основе истории продаж, сезонности, устойчивого роста спроса, текущих остатков, товаров в пути, категорий товаров, прогноза по приросту и оценки упущенного спроса в периоды отсутствия товара формирует рекомендованные заказы поставщикам. Должен выявлять разовые крупные заказы (включая крупные продажи одному клиенту) и исключать их из расчёта регулярной потребности.

## Вход → выход
**Вход:** история продаж (дата, артикул, количество, обезличенный клиент, цена), текущие остатки по складам, периоды отсутствия товара (stockout) по артикулам, справочник поставщиков и сроков поставки, материальная ведомость из 1С.

**Выход:** список рекомендованных заказов (артикул, поставщик, рекомендуемое количество, обоснование, срочность) в виде таблицы/дашборда с возможностью экспорта.

## Данные
Партнёр предоставит отчёт V2 и данные по динамике продаж (образец; полный набор и дата выдачи — по согласованию). Поля: дата продажи, артикул, наименование, количество, цена, обезличенный ID клиента, склад, остаток на дату. Допустимы синтетические данные с реалистичным распределением.

## Must have (и как проверяет жюри)
1. **Базовая потребность** по каждому артикулу с учётом всех данных (история, остатки, в пути, категории, прогноз прироста). *Проверка:* изменение любого источника (например, объёма в пути) отражается на результате.
2. **Сезонность и устойчивый рост.** *Проверка:* для сезонного товара прогноз отражает сезонный паттерн, а не среднее.
3. **Компенсация упущенного спроса при stockout.** *Проверка:* для артикула со stockout потребность выше, чем по «сырым» продажам.
4. **Исключение разовых крупных заказов.** *Проверка:* искусственно добавленный крупный заказ не даёт существенного роста регулярного количества.
5. **Список заказов по поставщикам с обоснованием.** *Проверка:* у каждой строки есть объяснение количества; разбивка по поставщикам.

## Опционально
Приоритизация по риску дефицита; минимальная партия и условия поставщика; визуализация трендов по категориям; автоматическая выгрузка/рассылка заказа поставщику.

## Ограничения
**Нельзя:** отправлять заказ поставщику без подтверждения сотрудника; использовать неанонимизированные данные клиентов.
**Обязательно:** приватность данных, объяснимость расчёта, устойчивость к аномалиям и выбросам, совместимость выходного формата с учётной системой компании (1С).
