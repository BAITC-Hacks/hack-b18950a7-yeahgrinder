# Задача: интерфейс MVP — рекомендованные заказы поставщикам

Ты делаешь интерфейс на хакатоне. До защиты около 4 часов. Цель — не красивый код,
а демо, которое жюри увидит глазами и в котором менеджер закупа без объяснений поймёт,
что заказать и почему.

## Контекст

Кейс ТОО «Электрокомплект» (ekt.kz). Менеджер отдела закупа сейчас считает пополнение
склада в Excel — долго и редко, отсюда излишки и дефицит. Наш сервис считает рекомендованный
заказ по каждому из ~2 800 товаров поставщика ИЭК: чистит историю продаж от разовых крупных
сделок, досчитывает спрос в месяцы без товара, учитывает сезонность, тренд, остатки и товары
в пути. Расчёт уже готов и лежит в `engine/` — его делает другой человек, **ты его не
трогаешь**. Полный кейс — `docs/CASE.md`.

Пользователь — **менеджер закупа, не аналитик**. Он откроет экран, чтобы ответить на три
вопроса: что заказать срочно, сколько, и можно ли этой цифре верить. Всё, что не помогает
ответить на них, — на второй план.

## Стек и файлы

Python + **Streamlit**. Твои файлы — `app.py` и папка `ui/` (если захочешь разнести код).
В `app.py` уже есть рабочий драфт: форма параметров с кнопкой «Сохранить», таблица,
экспорт, график. Бери его за основу и доводи до MVP ниже, а не переписывай с нуля.

Запуск: `.venv/bin/streamlit run app.py`. Данные — распаковать `IEK.zip` в `data/raw/IEK/`.

## Как получать данные

```python
from engine.compat import load, DataError
from engine.compat import Params, compute

ds = load()                  # ~0.3 с из кеша; при отсутствии данных — DataError с текстом для человека
res = compute(ds, Params())  # ~1 с на все товары
```

`Params(review_days=30, lead_days=30, service_level=0.95, growth_pct=0.0, oneoff_k=6.0, groups=None)`

`res.orders` — одна строка на товар:

| колонка | смысл |
|---|---|
| `code`, `article`, `name`, `unit` | код 1С, артикул ИЭК, название, единица |
| `group`, `group_name`, `supplier` | категория, её название, поставщик |
| `base_month` | регулярный спрос в месяц |
| `forecast_need`, `safety_stock` | прогноз на срок поставки + период; страховой запас |
| `stock_now`, `in_transit`, `moq` | остаток, в пути, кратность |
| `order_qty` | **рекомендуемый заказ** (0 — не нужно) |
| `days_cover`, `lead_days` | на сколько дней хватит запаса; срок поставки |
| `urgency` | `критично` / `высокая` / `плановая` / `не нужно` |
| `reason` | полное обоснование текстом |
| `n_oneoff`, `lost_qty` | сколько разовых строк исключено; сколько спроса досчитано |

`res.history` — для графика: `code, month, raw_qty, oneoff_qty, lost_qty, clean_qty, forecast`.
`res.oneoffs` — исключённые строки продаж: `date, doc, code, qty, threshold`.
`res.warnings` — список оговорок (например, «нет файла остатков»). Показывать всегда, если не пуст.
`res.errors` — товары, которые не удалось посчитать.

Если тебе нужно поле, которого нет, — не вычисляй его в UI сложной логикой, попроси у
владельца `engine/`. Простые производные (короткая строка обоснования из колонок) — делай сам.

## Что должно быть в MVP

### 1. Экран «Заказы» — главный

- **Сверху 3–4 цифры крупно:** позиций к заказу, из них критично, исключено разовых
  строк продаж, товаров с досчитанным упущенным спросом.
- **Вкладки по срочности:** «Критично» (открыта по умолчанию), «Высокая», «Плановая»,
  «Все». Менеджер не должен видеть 1 000 строк сразу.
- **Поиск** по названию/коду/артикулу и фильтр категорий.
- **Таблица, 6–7 колонок, не больше:** срочность (цветной значок), товар (название + код
  мелко), остаток, в пути, хватит на N дней, **к заказу** (редактируемая), короткое
  обоснование в одну строку. Короткое собери сам из колонок, например:
  `Спрос ~120 шт/мес · запаса на 8 дн · поставка 30 дн`. Полное — в карточке.
- Группировка по поставщику (сейчас поставщик один — ИЭК, но код должен быть готов к
  нескольким).

### 2. Карточка товара — «почему столько»

Открывается по выбору строки. Это главный экран для доверия, на демо жюри смотрит именно его.

- Расчёт **как формула**, крупно: `прогноз 1 200 + страховой 300 − остаток 150 − в пути 400
  = 950 → кратность 50 → заказ 950`.
- Полный текст `reason`.
- **График по месяцам:** регулярные продажи, исключённые разовые (серым), досчитанный
  упущенный спрос (оранжевым), прогноз (зелёным). Легенда на русском. Это визуальное
  доказательство must-have: видно, что выброс вырезан, а провал без товара досчитан.
- Таблица исключённых строк продаж из `res.oneoffs` (дата, документ, количество, порог),
  если есть.

### 3. Утверждение и выгрузка

- Правки количества в таблице сохраняются при переключении вкладок и фильтров
  (`st.session_state`), а не сбрасываются.
- Кнопка **«Утвердить заказ»** → окно подтверждения с итогом (позиций, изменено вручную
  столько-то) → после подтверждения кнопка скачивания **XLSX** и отметка «утверждён,
  дата-время».
- Колонки XLSX для импорта в 1С: `Код 1С, Артикул, Наименование, Ед., Количество,
  Поставщик, Срочность`. Только строки с количеством > 0.
- **Никакой автоматической отправки поставщику** — это прямо запрещено кейсом.

### 4. Параметры

- Форма с кнопкой **«Сохранить»** — уже есть, параметры применяются только по ней. Оставь.
- На виду только то, что понятно менеджеру: **категории** и **прогноз прироста, %**.
  Остальное (срок поставки, период до следующего заказа, уровень сервиса, строгость
  отсечения разовых заказов) — в свёрнутом блоке «Настройки для аналитика», с подсказками
  человеческим языком.

### 5. Оговорки и ошибки

- `DataError` при загрузке → понятное сообщение и инструкция, никакого трейсбэка
  (в драфте уже есть).
- `res.warnings` → заметный, но не кричащий блок «Расчёт сделан с оговорками».
- Ничто в интерфейсе не должно падать с красным трейсбэком на демо.

### 6. Вкладка «Проверки»

Заведи вкладку-заглушку. Содержимое (5 проверок must-have) делает другой поток в `checks/`
— ты только вызываешь их функцию, когда она появится.

## Скорость

- `load()` — через `@st.cache_resource`, `compute()` — через `@st.cache_data` по параметрам.
  Пересчёт только по «Сохранить».
- Не строй график и не фильтруй `res.history` по всем товарам — только по выбранному.
- Цель: переключение вкладок и выбор товара — мгновенно, «Сохранить» — до 3 секунд.

## Не делать

- Не трогать `engine/` и `checks/` — это чужие файлы, будут конфликты в git.
- Не добавлять авторизацию, базу данных, отправку почты, отдельный фронтенд-фреймворк.
- Не показывать менеджеру английские названия колонок и технические термины (MAD, σ, z).
- Не прятать ошибки: если что-то не посчиталось — показать, а не молча выкинуть.

## Готово, когда

1. Открыл → сразу вижу критичные позиции ИЭК, 6–7 понятных колонок.
2. Выбрал «Петля металлическая LOOP» → на графике видно исключённые 210 000 шт (июнь 2025),
   в тексте — «Исключено разовых заказов».
3. Поменял количество у двух товаров, переключил вкладку — правки на месте.
4. Утвердил → скачал XLSX, открыл в Excel — колонки как выше, только ненулевые строки.
5. Поменял прирост на +20% → «Сохранить» → цифры выросли, до 3 секунд.
6. Ни одного трейсбэка за весь сценарий.

Проверяй каждый пункт, открывая приложение в браузере, а не на словах.
