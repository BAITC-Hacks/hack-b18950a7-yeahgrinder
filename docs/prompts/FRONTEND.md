# Задача: доделать интерфейс SupplyAI (`web/`) на реальных данных

Ты дорабатываешь интерфейс на хакатоне, до защиты около 2,5 часов. Интерфейс уже есть и уже
работает на реальных данных — задача довести его до демо, а не переписывать.

## Главный принцип

**Расчёт и бизнес-логику не менять.** Фронт показывает уже работающий конвейер: данные →
очистка → прогноз → досчёт дефицита → исключение разовых сделок → остатки и путь → заказ →
объяснение. Главный риск — не алгоритм, а то, что жюри увидит красивую таблицу и не поймёт,
сколько логики под ней. Менеджер должен за 5–10 секунд понять: сколько позиций требуют заказа,
где самый высокий риск, и почему конкретной позиции предложено именно такое количество.

## Что есть сейчас

Кейс — `docs/CASE.md`. 3 561 товар двух поставщиков: **IEK (ИЭК)** и **Systeme Electric (SE)**.

- `web/` — интерфейс SupplyAI (Аслан; в основной репозиторий попадает после его пуша обновления):
  чистый JS-модуль, без сборки. `index.html`, `app.js`
  (экраны), `mockDashboard.js` (провайдер данных + демо-набор на случай, если API недоступен),
  `export.js` (XLSX в браузере), `styles.css`.
- `api.py` — FastAPI: отдаёт страницу `web/` с корня и данные на `/ui/data`; плюс API сервиса
  (расчёты, утверждения, правила, what-if, чат).
- `web_data.py` — адаптер: результат расчёта → товары ровно в форме демо-набора.
- `engine/`, `service.py`, `agent/`, `export/`, `tests/` — **не твои, не трогать**.

**Запуск:**
```bash
.venv/bin/pip install -r requirements.txt
.venv/bin/uvicorn api:app --port 8000        # открыть http://127.0.0.1:8000
```
Данные: `IEK.zip` → `data/raw/IEK/`, `Systeme electric.zip` → `data/raw/SE/`. Первый расчёт для
интерфейса ~12 с (греется в фоне при старте), дальше из кэша. Если API не отвечает, интерфейс
показывает демо-набор и плашку «Демо-данные».

**Твои файлы:** `web/`. Если нужно поле, которого нет в `/ui/data`, — не вычисляй сложной логикой
в JS, попроси добавить в `web_data.py` (Аят). Подписи и простые производные — сам.

## Данные: `GET /ui/data?growth_pct=20`

Ответ: `{meta, products, sources}`. `products` — одна запись на товар, форма как в демо-наборе:

| поле | смысл |
|---|---|
| `id` = `sku` | код 1С |
| `article`, `name`, `unit`, `supplier` | артикул, название, ед., `IEK` / `Systeme Electric` |
| `category` | товарная группа (первое слово названия группы: «Выключатель», «УЗО»…) |
| `abc` | категория важности: SE `1/2/3/5/7` (из файла менеджера), IEK `A/B/C` |
| `stock_current`, `in_transit_in_horizon` | остаток; в пути с приходом в горизонте |
| `cover_days` | на сколько дней хватит остатка (`null` — спроса нет) |
| `lead_time_days`, `horizon_days` | срок поставки; горизонт = срок + период до следующего заказа |
| `forecast_horizon`, `safety_stock`, `need` | прогноз на горизонт, страховой запас, потребность до округления |
| `moq`, `recommended_qty` | кратность; **рекомендуемый заказ** |
| `urgency` | `CRITICAL` / `HIGH` / `PLANNED` / `OK` |
| `order_value` | сумма заказа по себестоимости, ₸ — только SE (у IEK `null`) |
| `reason_text` | полное обоснование от движка |
| `warnings`, `quality` | оговорки по товару; «Нужна проверка» / «Есть допущения» / «Данные полные» |
| `excluded_events` | разовые сделки: `date`, `doc`, `qty`, `threshold` (учтено), `excess` (исключено) |
| `lost_qty`, `restored_text` | досчитанный спрос за месяцы без товара и текст по месяцам |
| `history`, `history_label` | 8 точек для графика `{month, raw, clean, forecast}` и подпись периода; если разовая сделка или дефицит были давно — окно сдвинуто на них («Архив: …») |
| `growthScenario` | `{forecast_horizon, recommended_qty}` при приросте `growth_pct` (по умолчанию +20%) — посчитано движком |

`meta`: `asOf`, `reviewDays`, `growthPct`, `live: true`, `leadText` (срок поставки по
поставщику с источником), `orderValue` (итог ₸ по поставщику), `warnings`.

**На текущих данных для самопроверки:** IEK — к заказу 1 015, критично 456, из них без товара в
пути 346, разовые сделки исключены у 606 товаров; SE — 259 / 94 / 88 / 184, сумма ≈159 млн ₸.

## Обновление фронта (архив `SupplyAI-frontend.zip`, пушит Аслан)

Сделано и проверено в Chromium в двух режимах — с API (реальные данные) и без него (демо-набор):

- **Провайдер данных** (`mockDashboard.js`): берёт `/ui/data`; если API недоступен — демо-набор и
  плашка «Демо-данные». В шапке и внизу — «Данные 1С» / выгрузка, когда данные живые.
- **Убраны привязки к демо-товарам:** `iek-loop`, горизонт 60 дн., «июль: 4 → 52 шт.», сроки
  «24–30 дней», «демо-набор» в подписях — всё из полей товара и `meta`.
- **KPI по поставщикам** на обзоре: к заказу, критично, **критично и ничего нет в пути**, разовые
  сделки исключены, для SE — сумма ₸. Подсказки к каждой; клик открывает «Закупки» с нужным
  фильтром. Пометка про оценочный остаток ИЭК.
- **Фильтры в «Закупках»:** товар в пути (есть / ничего нет), была разовая сделка, категория
  важности (`abc`); сортировка — срочность, затем количество.
- **Карточка:** плитки «Срок поставки» с источником, «Горизонт расчёта», «Категория важности».
- **Утверждение:** поле **«Утвердил (ФИО)»** — без него кнопка не активна; ФИО и время в плашке,
  в CSV и на отдельном листе «Утверждение» в XLSX (лист «Заказ» — без изменений, для 1С).
- **Экспорт CSV** (`;`, UTF-8 с BOM — открывается в Excel) рядом с XLSX.
- **Сумма по себестоимости** в черновике (SE); таблицы рисуют первые 300 строк с подсказкой.

## Интеграция с сервисом (сделано, Аят)

1. **Фронт в `web/`** основного репозитория — `api.py` раздаёт его с корня.
2. **Дизайн:** KPI поставщиков компактно — подпись, число, одна строка; полное пояснение во всплывающей
   подсказке; «Нет в пути» — красным, сумма ₸ SE — в шапке карточки; сноска про оценочный остаток с
   числом товаров. В таблицах «Запаса хватит»: «Нет в наличии» — красным, запас короче срока
   поставки — оранжевым. Обоснование в карточке — списком фактов вместо абзаца.
3. **«Что если…»** в карточке: срок поставки и доп. количество в пути → `POST /runs` (один раз за
   сессию) → `POST /runs/{run_id}/what-if` → «Заказ 110 → 190 шт (+80)». Ничего не сохраняет.
4. **Вкладка «Спросить помощника»** в карточке (только с живыми данными): подсказки-вопросы,
   `POST /runs/{run_id}/chat`, отметка «✓ числа сверены с расчётом» / «⚠ есть числа не из данных».
   Без ключа (`GET /health` → `ai.chat == false`) — объяснение, как включить.
5. **Утверждение через сервер — сознательно не сделано.** В сервисе решение принимается по всему
   заказу поставщика (около 1 000 позиций ИЭК с правками), а во фронте — по черновику из выбранных
   позиций. Отправка черновика как решения сервиса выгрузила бы и невыбранные позиции с
   рекомендованными количествами. Утверждение остаётся локальным (ФИО, XLSX с листом «Утверждение»,
   CSV); для серверного нужен режим «решение по списку позиций» в `service.decide`.

Проверено в Chromium: обзор, KPI и переходы по ним, фильтры, карточки, «что если», помощник без
ключа, черновик, утверждение с ФИО, XLSX и CSV — без ошибок в консоли.

Документация API — http://127.0.0.1:8000/docs.

## Демо-сценарий (2–3 минуты) — интерфейс должен проходить его без запинок
1. Обзор → строка KPI.
2. «Закупки», фильтр «Критично» → список.
3. «Петля металлическая LOOP» (IEK, `130200305_`) → «История спроса»: архив 2025, разовая продажа
   210 000 шт по накладной 20000064179 исключена из регулярного спроса; «Показать всплеск» —
   событие не удалено из истории.
4. «Выключатель 1кл о/у 10А IP54 AQUATIC» (IEK, `ярп40257`) → в апреле и мае 2026 товара не было,
   продажи 0 → досчитано 58 и 65 шт (в другие месяцы 25–97 шт); заказ 110 шт = прогноз 121 +
   страховой 100 − остаток 16 − в пути 100 → до кратности 10.
5. «Установочная коробка IMT35100» (SE, `030200192_`) → 226 800 шт, сумма ≈15,4 млн ₸; крупные
   накладные здесь регулярные — не исключены.
6. В черновик → «Подтвердить заказ» → XLSX для 1С.

## Не делать
- Не трогать `engine/`, `service.py`, `api.py`, `agent/`, `export/`, `tests/`, `web_data.py`
  (последний — через Аята).
- Не добавлять сборщики, фреймворки, внешние CDN, авторизацию, отправку поставщику.
- Не показывать менеджеру английские коды (`CRITICAL`, `ONE_OFF_INVOICE`) и термины (MAD, σ, z).
- Не прятать оговорки: честное ограничение повышает доверие.
- Проверять модули как модули: `cp web/app.js /tmp/x.mjs && node --check /tmp/x.mjs` — обычный
  `node --check app.js` ошибки в шаблонных строках не ловит.

## Готово, когда
1. Обзор: KPI по поставщикам с цифрами как в «самопроверке» выше; пометка про остаток IEK.
2. Демо-сценарий проходится за 2–3 минуты, в консоли браузера ни одной ошибки.
3. Фильтры «в пути» и «разовая сделка» работают; XLSX и CSV скачиваются.
4. Без ключа API всё, кроме чата, работает.
