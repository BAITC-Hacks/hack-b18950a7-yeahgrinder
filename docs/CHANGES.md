# Серверная часть для интерфейса SupplyAI (`web/`)

Фронт SupplyAI (Аслан) подключается к расчёту через API. **Сам фронт в этом коммите не лежит** —
его обновление Аслан пушит сам; после этого он кладётся в `web/` и раздаётся этим сервером.

- **Запуск:** `.venv/bin/uvicorn api:app --port 8000` → http://127.0.0.1:8000. Если в репозитории есть
  `web/`, страница раздаётся с корня; API — как раньше (`/docs`). Streamlit (`app.py`) — запасной.
- **`GET /ui/data?growth_pct=20`** (`api.py`) → `web_data.py` превращает результат `engine/run.py` в
  товары формы демо-набора фронта (`web/mockDashboard.js`): остаток, путь, прогноз, заказ,
  срочность, обоснование, исключённые сделки, досчитанный спрос с текстом по месяцам, 8 точек
  истории для графика (у товаров с давней разовой сделкой — архивное окно на событии), сценарий
  +20%, считанный движком. Первый расчёт ~12 с (греется в фоне при старте), дальше из кэша; ответ
  сжат gzip (6 МБ → 0,4 МБ).
- **`engine/models.py` / `engine/run.py`:** в `OrderLine` добавлены необязательные поля для
  интерфейса — `group_name`, `category`, `service_level`, `unit_cost`, `order_value`, `stock_source`,
  `lead_source`. Старые расчёты без них валидны.
- Контракт `/ui/data` и задачи по фронту — `docs/prompts/FRONTEND.md`.

# Слияние с веткой `backend` (Алдияр) — один расчёт на весь проект

Ветка `backend` влита в `main`, сама ветка сохранена. Раньше в проекте было два движка с разными
цифрами (коробка SE: 226 800 в интерфейсе против 7 200 в чате). Теперь **все количества считает
`engine/calc.py`**, а сервис, API и агент Алдияра получают их через мост `engine/run.py`.

**Что где:**

| Файл | Что делает |
|---|---|
| `engine/load.py` + `engine/calc.py` | загрузка и расчёт (как в c31f394 + поля для агента) |
| `engine/run.py` | **мост**: `compute(ds, Params, rules)` в схеме `OrderLine` (pydantic) для сервиса/API/агента; `agent_tables(ds)` — таблицы для SQL-инструмента агента |
| `engine/models.py`, `engine/validate.py` | контракты Алдияра без изменений, кроме двух полей ниже |
| `engine/loader.py` | от него используется только распознавание файлов по заголовкам |
| `service.py`, `api.py`, `agent/`, `export/` | код Алдияра; снимок данных расчёта теперь `runs/<id>/dataset.pkl` |
| удалены | `engine/anomalies.py`, `forecast.py`, `prepare.py`, `replenish.py`, `explain.py`, `compat.py`, `tests/test_compat.py` (остались в ветке `backend`) |

**Для агентов, которые пишут код:**
- Интерфейс (`app.py`) — `from engine.calc import Params, compute`, `from engine.load import load`.
  Сервис/API/агент — `from engine.run import compute` + `engine.models.Params`. Цифры одинаковые.
- `engine.models.Params.lead_time_days` теперь `{"IEK": None, "Systeme Electric": None}` —
  `None` = срок из данных (ИЭК 24 дн. по заказам в пути, SE 45 дн. допущение); число — переопределение.
- `engine.models.Params.service_z` теперь `None` = уровень сервиса по категории (1/A 98%, 2/B/5 95%,
  3/C 90%); число — один z для всех. В `config.yaml` оба поля `null`.
- Поставщики в API/агенте — `IEK` и `Systeme Electric`; в `engine/calc.py` и интерфейсе — `ИЭК` и
  `Systeme Electric`. Перевод — `engine.run.SUPPLIER_OUT` / `SUPPLIER_IN`.
- `excluded_events` у строки: `type` (`ONE_OFF_INVOICE` / `STAT_SPIKE`), `month`, `date`,
  `doc_no`, `invoice_qty`, `clean_qty`, `excluded_qty`, `threshold`.
  `restored_events`: `month`, `raw_qty`, `qty` (досчитано), `clean_qty`.
- Разовая строка теперь **исключается целиком** (раньше — заменялась типичной строкой).
- Файлы SE переименовывать не нужно — распознаются по заголовкам.
- `requirements.txt` — версии Алдияра (pandas 2.x), кроме `altair>=6,<7`: altair 5 не работает на
  Python 3.14. После `git pull` — `.venv/bin/pip install -r requirements.txt`.

**Скорость:** сервис на реальных данных — 3,9 с на расчёт (раньше 54 с), what-if по товару — 0,2 с.
**Тесты:** 29, все зелёные. Must-have тесты Алдияра перенесены на этот расчёт (сценарии меняют
накладные, а не месячный отчёт — спрос берётся из накладных) и дополнены: остаток, прирост,
категория, регулярный крупный покупатель.
**README** переписан в части методологии, алгоритма выбросов, данных и допущений под реальный расчёт.

# Что изменилось: 353389d → c31f394

Коротко: движок теперь считает **двух поставщиков** (ИЭК и Systeme Electric), учитывает
**категории товаров** в страховом запасе и строже определяет выбросы и дефицит. Контракт
`compute()` расширен новыми колонками, старые колонки на месте и значат то же самое —
кроме трёх мест, отмеченных ⚠️ ниже.

## Что сделать после `git pull`

1. Распаковать `Systeme electric.zip` в `data/raw/SE/` (без папки `__MACOSX`) и
   переименовать файлы — имена в архиве искажены. Команда внутри `data/raw/SE/`:
   `python3 -c "import os,unicodedata;[os.rename(f,unicodedata.normalize('NFC',f).encode('mac_cyrillic').decode('cp866')) for f in os.listdir('.') if not f.isascii()]"`
2. `IEK.zip` остаётся в `data/raw/IEK/`. Итоговая структура: `data/raw/IEK/*.xlsx`,
   `data/raw/SE/*.xlsx`.
3. Первый запуск перечитает Excel (~15 с): формат кеша поменялся. Дальше ~0,3 с.

## ⚠️ Что может сломать ваш код

| Было | Стало | Что поправить |
|---|---|---|
| `load()` читал `data/raw/IEK/`; `DATA_DIR` указывал на папку ИЭК | `load()` читает `data/raw/`, каждая подпапка — поставщик. `DATA_DIR` указывает на `data/raw` (папка одного поставщика напрямую тоже работает) | Если где-то захардкожен путь `data/raw/IEK` — убрать |
| `Params.lead_days = 30` — срок по умолчанию | `Params.lead_days = None` — срок из данных поставщика; число — один срок для всех товаров | Не передавать 30 «по умолчанию», иначе перебьёте сроки из данных. В `app.py` это чекбокс «Срок поставки из данных» |
| `Params.service_level` — для всех товаров | Только для товаров без категории. Основной — `Params.service_by_category` | Ползунок «уровень сервиса» теперь второстепенный |

Ещё: `ds.company_season` остался как совместимость, но правильно — `ds.supplier_season`
(словарь поставщик → 12 коэффициентов). В `res.oneoffs` колонка `doc` теперь
`"<номер>/<год>"`: номера накладных в 1С сбрасываются каждый год.

## Новое в контракте

**Params:**
- `suppliers: list[str] | None` — фильтр: `["ИЭК"]`, `["Systeme Electric"]`, `None` — все.
- `service_by_category` — уровень сервиса по категории: 1/A → 98%, 2/B/5 → 95%, 3/C → 90%.
- `no_auto_categories = ("7",)` — категории без автозаказа (новинка/выведен).

**Новые колонки `res.orders`:**

| колонка | смысл |
|---|---|
| `supplier` | теперь реально разный: `ИЭК` или `Systeme Electric` |
| `category` | SE — из файла менеджера (1/2/3/5/7); ИЭК — ABC по числу накладных за 12 мес. |
| `service_level` | уровень сервиса, который применён к товару |
| `unit_cost`, `order_value` | себестоимость и сумма заказа в ₸ — **только SE**, у ИЭК цен нет (пусто) |
| `stock_source` | `из выгрузки` (SE — остаток на 22.09 дан) или `оценка` (ИЭК — остаток на 1-е число минус продажи месяца) |
| `lead_source` | `по заказу в пути` / `из дат заказов в пути` / `из настроек` / `допущение` |
| `flags` | список кодов для значков и агента (ниже) |

**`flags`:** `ONE_OFF_EXCLUDED` — исключены разовые продажи · `STOCKOUT_RESTORED` —
досчитан спрос за месяцы без товара · `TREND_UP` / `TREND_DOWN` — устойчивый тренд ·
`STOCK_ESTIMATED` — остаток оценочный · `LEAD_ASSUMED` — срок поставки допущение ·
`MOQ_MISSING` — кратности нет в справочнике, взята 1 · `MOQ_OVERSHOOT` — округление до
кратности добавило больше 50% · `CATEGORY_NO_AUTO` — категория 7, решает менеджер.

**Dataset (если лезете в `ds` напрямую):** `ds.items` получил `supplier`, `category`,
`category_source` (`file`/`abc`), `moq_known`, `unit_cost`. Новые поля:
`ds.stock_current` (код → текущий остаток, есть у SE), `ds.lead_default`
(поставщик → (дней, источник)), `ds.supplier_season`.

## Что поменялось в расчёте (цифры другие — это ожидаемо)

1. **Сезонность:** своя у каждого поставщика; группы товаров считаются внутри поставщика.
   Неполный сентябрь 2026 (данные до 22.09) досчитан ×30/22 — коэффициент сентября у ИЭК
   1,10 вместо 0,97.
2. **Срок поставки ИЭК** — из дат заказов в пути: медиана, взвешенная по количеству,
   = **24 дня** (раньше было 30 по умолчанию). SE — **45 дней, допущение** (дат заказа нет).
3. **Разовые заказы:** если крупные строки у товара повторяются в 3+ разных месяцах — это
   обычный спрос крупного покупателя, не выброс. Пример: коробка SE `030200192_` уходит
   по 60–90 тыс. шт. регулярно — больше не режется. «Петля LOOP» 210 000 шт. — по-прежнему
   исключена.
4. **Дефицит (stockout):** месяц досчитывается, только если остаток на начало = 0 **и**
   продажи ниже половины обычного. Раньше хватало нулевого остатка.
5. **Страховой запас** зависит от категории; категория 7 → заказ 0.
6. **Текущий остаток SE** — как в модели менеджера: свободный + витрина + ТЗ + розничный.

## Отказоустойчивость (как было, но теперь по поставщикам)

Нет файла продаж у поставщика → поставщик пропускается с оговоркой; нет ни одного →
`DataError`. Любой другой файл отсутствует или битый → расчёт идёт без него, причина в
`res.warnings` с префиксом поставщика («ИЭК: …», «Systeme Electric: …»). Колонки ищутся
по заголовкам, поэтому разные форматы выгрузок ИЭК и SE читаются одним кодом.

## Не изменилось

Сигнатуры `load()` / `compute()`, все прежние колонки `res.orders`, формат
`res.history` и `res.oneoffs` (кроме `doc`), значения `urgency` (`критично` / `высокая` /
`плановая` / `не нужно`), кнопка «Сохранить» в `app.py`.

Подробно о данных — `docs/DATA.md`, контракт целиком — `docs/PLAN.md`.
