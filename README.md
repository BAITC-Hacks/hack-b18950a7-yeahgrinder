# QadamSupply — автоматический расчёт заказов поставщикам

Кейс ТОО «Электрокомплект» (HackAlem AI). Сервис по истории продаж, остаткам и товарам в пути
рассчитывает рекомендованные заказы поставщикам IEK и Systeme Electric для склада Алматы,
исключает разовые крупные продажи, досчитывает спрос в месяцы без товара и объясняет каждую цифру.
Менеджер проверяет, правит и утверждает заказ; **отправки поставщику в системе нет**.

```text
Python (pandas)  все количества: очистка, прогноз, заказ, кратность, срочность, обоснование
OpenAI (опц.)    чат «почему столько?» и «что если» — только через инструменты, числа не считает
NVIDIA (опц.)    независимая проверка ответов чата, количества не меняет
Менеджер         утверждает / правит / отклоняет
```

Без ключей API работает всё, кроме чата: расчёт, интерфейс, утверждение, экспорт.

## Запуск

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env          # указать папки с выгрузками, ключи — по желанию
.venv/bin/streamlit run app.py              # интерфейс
.venv/bin/uvicorn api:app --reload          # HTTP API, документация на /docs
.venv/bin/python -m pytest -q               # тесты
```

**Данные.** В `.env` задаются `IEK_DATA_DIR` и `SE_DATA_DIR` — папки с xlsx-выгрузками партнёра
(по умолчанию `data/raw/IEK` и `data/raw/SE`). Имена файлов не важны: загрузчик узнаёт файл по
заголовкам колонок, поэтому «кракозябры» в именах из архива не мешают. Первый разбор xlsx занимает
около 20 с, дальше данные читаются из кэша `data/processed/`. Данные партнёра в git не попадают.

**Ключи (необязательно):** `OPENAI_API_KEY` + `OPENAI_MODEL` — чат; `NVIDIA_API_KEY` +
`NVIDIA_MODEL` — критик. Ключи только в `.env`, в коде и конфиге их нет.

## Какие данные используются

| Источник | Для чего |
|---|---|
| Динамика продаж (строки накладных) | поиск разовых крупных продаж; спрос по SKU, которых нет в месячном отчёте |
| Ежемесячные продажи | ряд спроса по месяцам |
| Ежемесячные остатки (на 1-е число) | поиск месяцев без товара (stockout) |
| Товар в пути | вычитается из потребности, если приходит в горизонте заказа |
| MOQ / кратность | округление заказа |
| Сезонность | помесячные коэффициенты поставщика |
| Файл менеджера SE | текущий свободный остаток и резерв |

Изменение любого источника меняет итог — это проверяется тестами (см. ниже).

## Методология расчёта

Для каждого SKU, одним пакетом по всем товарам (≈ 20 с на 3 900 SKU):

1. **Ряд спроса.** Помесячные продажи за последние 18 полных месяцев, возвраты не считаются
   спросом. Текущий месяц неполный (данные до 22.09) и в расчёт не входит.
2. **Упущенный спрос (stockout).** Месяц считается дефицитным, если остаток на начало или конец
   месяца нулевой (или меньше 25% обычного спроса) **и** продажи упали ниже половины обычного
   уровня. Такой месяц восстанавливается до `медиана × сезонность месяца` и не участвует в
   оценке нормального уровня.
3. **Разовые крупные продажи** — см. следующий раздел.
4. **Прогноз.** Уровень — взвешенное среднее очищенного спроса без сезонности за последние
   6 месяцев (свежие месяцы весят больше). Тренд — отношение последних 6 месяцев к предыдущим 6,
   ограничено 0,7…1,5 и применяется, только если оба квартала полугодия идут в одну сторону.
   Прогноз месяца = уровень × тренд × (1 + прирост %) × сезонный коэффициент.
   Горизонт = срок поставки + период до следующего заказа, считается по календарным дням:
   для IEK при сроке 30 дн. и периоде 30 дн. это остаток сентября, октябрь с коэффициентом ×1,24
   и часть ноября — прогноз видит октябрьский пик, а не среднее.
5. **Заказ.**
   ```text
   страховой запас = z × σ(спроса) × средняя сезонность горизонта × √(горизонт / 30)
   позиция         = свободный остаток + товары в пути с приходом в горизонте
   потребность     = прогноз на горизонт + страховой запас − позиция
   заказ           = 0, если потребность ≤ 0, иначе вверх до кратности MOQ
   ```
   Кабель «305 м … закупаются бухтами» округляется до 305 м. Если округление добавило больше
   50% к потребности — флаг «проверить вручную».
6. **Срочность.** `CRITICAL` — товара нет или запаса с учётом пути не хватит до прихода новой
   поставки; `HIGH` — хватит меньше чем на срок поставки + половину периода; `PLANNED` — заказ
   нужен; `OK` — не нужен.
7. **Обоснование** собирается кодом из тех же чисел для каждой строки: прогноз, база, тренд,
   сезонность по месяцам, страховой запас, остаток, путь, исключённые накладные, восстановленные
   месяцы, допущения. LLM для него не нужен.

## Алгоритм исключения выбросов (разовые крупные продажи)

В данных нет клиента, поэтому «крупная продажа одному клиенту» определяется как месяц, в котором
продажи аномально высоки и основную часть даёт одна накладная.

1. Спрос очищается от сезонности: `d = продажи месяца / коэффициент месяца`.
2. Нормальный уровень — медиана `d`, разброс — MAD (медианное абсолютное отклонение × 1,4826);
   обе величины устойчивы к самим выбросам. Месяцы дефицита в оценку не входят.
3. Месяц — кандидат в выбросы, если одновременно:
   `d > медиана + 3,5 × MAD`, `d > 2 × медиана` и продажи ≥ 20 единиц.
4. Если кандидаты идут **3 месяца подряд** — это устойчивый рост, а не разовый заказ; не чистим.
5. Атрибуция: если одна строка накладной дала ≥ 50% продаж месяца — событие `ONE_OFF_INVOICE`
   (номер, дата и количество накладной попадают в обоснование), иначе `STAT_SPIKE`.
6. Месяц не удаляется, а срезается до потолка `(медиана + 3,5 × MAD) × сезонность`; исходное
   значение сохраняется и показывается на графике.
7. **Редкий спрос:** если больше половины месяцев без продаж, нормальный уровень берётся по
   месяцам с продажами — иначе нулевая медиана превратила бы любую продажу в «выброс».

Для товаров, которые **регулярно** продаются крупно (установочная коробка SE — 60–90 тыс. шт.
на накладную), медиана высокая, и крупная накладная выбросом не считается.

**Ограничение:** если у товара меньше трёх месяцев с продажами, сравнивать всплеск не с чем, и он
не чистится — строка получает флаг `SHORT_HISTORY` («проверить вручную»). Пример из данных:
накладная №20000064179 от 09.06.2025 — 210 000 шт. «Петля металлическая LOOP», единственная
продажа товара; заказ по нему 0, потому что за последние 12 месяцев продаж нет (`NO_DEMAND`).

## Проверки must-have (`tests/test_musthave.py`)

| # | Требование кейса | Тест |
|---|---|---|
| 1 | Учтены все источники | `test_transit_reduces_order`: +500 шт. в пути → заказ меньше на ≈500 |
| 2 | Сезонность и рост | `test_seasonality_peak`: прогноз октября > 1,2 × базы при сезонном коэффициенте 1,24 |
| 3 | Упущенный спрос | `test_stockout_restores_demand`: при нулевом остатке база и заказ выше, чем по сырым продажам |
| 4 | Разовые заказы | `test_one_off_spike_ignored`: накладная ×10 меняет заказ не больше чем на 10%, помечена `ONE_OFF_INVOICE` |
| 5 | Список по поставщикам с обоснованием | `test_every_line_explained_and_grouped`: у каждой строки есть обоснование, количество кратно MOQ |

Дополнительно: неполный месяц не влияет на заказ, путь после горизонта не вычитается,
устойчивый рост не чистится, редкий спрос не обнуляется, агент и API (`tests/test_agent.py`,
`tests/test_api.py`).

## Утверждение и экспорт

Менеджер правит количество (проверяется кратность), утверждает или отклоняет с причиной; решение
и разница «рекомендация → утверждено» сохраняются в SQLite. Экспорт в XLSX доступен только после
утверждения: `Код 1с | Артикул | Наименование | Ед. | Кол-во | Кратность | Срочность | Обоснование`
+ лист «Параметры и допущения». Правило менеджера («минимум N по SKU») сохраняется и применяется
в следующих расчётах с отметкой в обосновании.

## Чат-агент

LangGraph: модель ⇄ инструменты, не больше 6 шагов. Инструменты только читают данные или считают
«что если» без сохранения: сводка, список заказов, объяснение по SKU, схема таблиц, SQL-запрос
(только `SELECT`, максимум 100 строк, без доступа к файлам), what-if, предложение правила
(сохраняет его только менеджер). Инструментов отправки заказа нет; вызов неразрешённого
инструмента отклоняется. Каждое число в ответе сверяется кодом с результатами инструментов —
выдуманные числа помечаются. Названия товаров передаются модели как данные, а не инструкции.

## Допущения и ограничения

- **Срок поставки** не дан явно: по умолчанию 30 дн. (IEK) и 45 дн. (SE), меняется в интерфейсе.
  По датам в файле «Путь» заказы IEK идут 12–40 дней.
- **Текущий остаток IEK** — оценка: остаток на 01.09 минус продажи с 01.09 по 22.09, поступления
  сентября не видны. Для SKU SE, которых нет в файле менеджера, — так же. Такие строки помечены
  `STOCK_ESTIMATED`.
- **Сезонность** — на уровне поставщика (в тенге), не по SKU.
- **Нет клиента и цены** в продажах — разовые заказы определяются по накладным, стоимость заказа
  не считается.
- **Месячный отчёт и накладные расходятся** (у SE заметно). Ряд спроса строится по месячному
  отчёту; накладные используются для атрибуции выбросов и для SKU, которых в отчёте нет.
- Период заказа 30 дн. и уровень сервиса 95% — параметры (`config.yaml`, интерфейс).
